# cljfx reactivity audit · 2026-11-23

Reviewed against `a7e414e`, with the project's [cljfx 1.10.6 and core.cache dependencies](../deps.edn#L12-L16). Paths such as `app.clj` and `views/…` below are relative to `src/laser_show/`. Seven parallel reviews covered subscriptions; events/effects; the shell and settings; dialogs and editors; grids and previews; external/runtime state; and document history and persistence. The render wiring and cache comparison were checked separately.

**Fix first:** a numeric edit that saves an unreadable show, a cue completion that can undo Stop, and two editors that write to the wrong target. **Then fix reactivity costs:** the starter Grid loses nearly its entire working set on unrelated updates, and explicit context props can keep old state snapshots reachable. The [state-outcome probes](probes/cljfx_state_outcomes_2026_11_23.clj) and [cache probes](probes/cljfx_reactivity_2026_11_23.clj) reproduce the main results in fresh, headless JVMs.

## The intended loop

**The application already has the right foundation.** cljfx doesn't own a global database. This application owns one: an atom containing a cljfx context over its immutable state map. A control sends an intent; the handler reads the state *when the event is handled*; an effect commits the result; cljfx renders on the JavaFX thread. The part most easily missed is that the component's **own** `:fx/context` records what that component depends on.

| Boundary | What cljfx 1.10.6 provides | How this app uses it |
|---|---|---|
| Database → renderer | `fx/create-context`; `fx/create-app` mounts the context atom, installs `wrap-context-desc` and uses `fn->lifecycle-with-context`. `swap-context`/`reset-context` derive a new context while retaining memoized work. | [state/core.clj:38–51](../src/laser_show/state/core.clj#L38) owns the atom and a bounded LRU; [state/core.clj:148–172](../src/laser_show/state/core.clj#L148) preserves the cache; [app.clj:95–112](../src/laser_show/app.clj#L95) mounts it. No second application database or new state framework is needed. |
| Renderer → view | `sub-val` is a direct read: on demand it is rechecked for a new context. Use a cheap lookup. A `sub-ctx` function can do expensive work; its recorded inputs are compared by value. The cache key includes the function and its arguments. Function components have the same dependency rules. | The BPM field [subscribes to `subs/bpm`](../src/laser_show/views/toolbar.clj#L116); [the selector](../src/laser_show/subs.clj#L57) uses a cheap extractor. Subscribe where the value is displayed. Pass plain IDs/values to children; let a context-aware child receive its own context. Finish subscription reads before returning, including reads in sequences or callbacks. |
| View → event → database | Map event handlers receive `:fx/event`. Co-effects provide input data; effects carry out writes and I/O. A function callback is fine when a JavaFX event genuinely needs translating. | The [BPM field](../src/laser_show/views/toolbar.clj#L127) produces `{:event/type :timing/set-bpm :bpm new-bpm}`. [The handler](../src/laser_show/events/handlers/timing.clj#L40) returns `{:state (assoc-in state [:timing :bpm] …)}`. The app supplies plain `:state` and `:time` [co-effects](../src/laser_show/events/core.clj#L674); its [ordered pipeline](../src/laser_show/events/core.clj#L655) runs `:state` before follow-up effects on [one event thread](../src/laser_show/events/core.clj#L773). A tick, future or device callback can dispatch an event; an independent write could be overwritten by the next snapshot commit. |
| Local interaction / external data | The pinned API also has `ext-state` (node-local state), `ext-watcher` (changes to another reference), and lifecycle hooks. A plain deref in a cached view does **not** establish a subscription. `ext-on-instance-lifecycle`'s `:on-created` runs once; `:on-advanced` runs when the **instance is replaced**, not whenever props change. | [Measured panes](../src/laser_show/views/components/measured.clj#L22) keep layout dimensions local. Keep device handles, in-progress gestures and frame-rate data at their owners; publish the values declarative UI actually displays. For native callbacks, use declarative event props or a lifecycle-managed binding to current data. |

## What the local skills and prompts say

**Guidance follow-up:** The four repository skills, refactoring prompt and review/planning instructions now use [Reactive state in this app](../docs/CLJFX_STATE_MANAGEMENT.md#reactive-state-in-this-app). The state, stale-closure and dev-tools guides were aligned as well. The observations and source line numbers in this report describe **the audited revision, `a7e414e`**.

- [Copilot instructions: state and closures](../.github/copilot-instructions.md#L25-L59) and [the planning rule](../.agents/rules/planning-guide.md#L18-L25) give the architecture: subscribe in the UI, use immutable snapshots/extractors in services, and write through event handlers. Distinguish saved/undoable document state, UI state, and runtime resources.
- [The Clojure refactoring prompt](../prompts/refactor-clojure-file.md#L83-L95) recommends `sub-val` for access, `sub-ctx` for derived values, eager view results and only short-lived local UI state. Its “read from the main database/state atom” should say **“read through the supplied `:fx/context` during rendering.”** Upstream's precise laziness rule is about deferring `sub-*` calls, not about every sequence of already-read data.
- [app-repl](../.agents/skills/app-repl/SKILL.md#L87-L106) treats `get-raw-state` as a diagnostic snapshot and shows `dispatch!`, `flush!` and `write-state!` for the REPL. [plorer](../.agents/skills/plorer/SKILL.md#L49-L61) and [targeted-ui-testing](../.agents/skills/targeted-ui-testing/SKILL.md#L50-L61) distinguish waiting for the event from waiting for the visible control. These are verification tools, not a model for how a view should read state.
- The app-specific rule in [CLJFX_STATE_MANAGEMENT.md:241–267](../docs/CLJFX_STATE_MANAGEMENT.md#L241-L267) is correct. The same guide's [summary](../docs/CLJFX_STATE_MANAGEMENT.md#L677-L691) still recommends worker writes before qualifying them; promote the app rule and show a worker dispatching a result first. Its [threading section](../docs/CLJFX_STATE_MANAGEMENT.md#L183-L215) is a local snapshot discipline. Upstream's **bound-context** restriction is about reading after a subscription returns, not a blanket assertion that every off-FX-thread read throws.
- [STALE_CLOSURES.md](../docs/STALE_CLOSURES.md#L83-L169) is right about callbacks installed once. Prefer its dispatch-with-ID pattern. The registry written during rendering is a fallback, not a general recipe: a cached description can be reused without running its function. A declarative event map also doesn't make a captured document or a “current + 1” value current again while it waits in the event queue.

## Render wiring and cache findings

**The 512-entry LRU is smaller than the starter Grid's working set.** I instrumented cljfx's actual context-aware component lifecycle, built the real starter root in a fresh headless JVM, and advanced it five times with a changed top-level key no view reads. The count is invocations of the application's view functions, **not** JavaFX nodes replaced or milliseconds:

| LRU capacity | Initial view calls | Calls on five unrelated updates |
|---:|---:|---|
| 512 (the [app setting](../src/laser_show/state/core.clj#L48-L51)) | 149 | 144, 149, 149, 149, 149 |
| 4,096 (comparison) | 149 | 91, 0, 0, 0, 0 |

The difference is whether the components' subscriptions survive until the next update. The narrower [per-cell selector tests](../test/laser_show/subs_test.clj#L70-L87) are valuable but exercise a tiny working set; they can't catch this. Retain a whole-view call-count regression, remove unstable/context-valued child props, and size the cache against Grid and an open editor. The comparison establishes eviction pressure; it doesn't establish that 4,096 is the right production value. [Runnable probes, including this one](probes/cljfx_reactivity_2026_11_23.clj).

1. **The dev renderer options silently do nothing.** [app.clj:60–85](../src/laser_show/app.clj#L60-L85) even announces the inspector, but [app.clj:103–112](../src/laser_show/app.clj#L103-L112) passes `:opts` and `:error-handler` to **`fx/create-app`**. Those are **`fx/create-renderer`** options. The [actual `create-app` implementation](https://github.com/cljfx/cljfx/blob/1.10.6/src/cljfx/api.clj#L584-L613) reads `:renderer-error-handler` and builds its own `:opts`. **Verified** by intercepting the call to `create-renderer` in the pinned library: neither supplied function reached it; passing `:renderer-error-handler` did. The default function lifecycle *is* context-aware, so normal reactivity works, but this wiring doesn't install the promised validation/F12 inspector or application error logger. Use the supported error key; install the dev resolver through renderer middleware or explicit renderer wiring while retaining the context-aware lifecycle and existing dispatcher. Correct [the dev-tools guide](../docs/CLJFX_DEV_TOOLS.md#L42-L57) and test the options delivered to the renderer. This was [previously noted and deferred](2026-11-16-output-runtime/03-phase3-event-reentry.md#L176-L178).
2. **The state read API promises tracking it cannot provide to views.** [state/core.clj:63–96](../src/laser_show/state/core.clj#L63-L96) labels `get-state` suitable for memoized UI; [get-in-state](../src/laser_show/state/core.clj#L174-L185) calls it. These functions dereference the *global* context, not the component's bound context. **Verified** with two memoized selectors in a fresh process. Both started at 120 BPM; after committing 142 BPM to the same context atom, the no-argument global-reader path still returned **120**, while the selector using its argument returned **142**. An event-time lookup can legitimately take a fresh snapshot; the error is advertising it as a render dependency. Make the snapshot/read distinction explicit at the API and in the prompt. Separately, `get-raw-state` and `reset-state-vals!` [extract `:cljfx.context/m` directly](../src/laser_show/state/core.clj#L162-L172): it works at 1.10.6, but upstream calls context representation private. Keep this no-cache compatibility boundary isolated and tested against upgrades; don't spread that key into components or create a separately writable mirror.
3. **Passing `:fx/context` as an ordinary child prop defeats child memoization.** See [the effect chain's list](../src/laser_show/views/dialogs/effect_chain_editor.clj#L127-L140), [the list's own sidebar](../src/laser_show/views/components/list.clj#L865-L873), and [the projector sidebar](../src/laser_show/views/tabs/projectors.clj#L516-L534), which even says it is required. cljfx keys a function component's subscription by its **incoming description**, then **overwrites** its `:fx/context` with the child's bound context. Including the parent's changing context changes the key without providing the child any information. **Verified** using real `fx/create-component`/`advance-component`, a parent subscribing to a counter and a child subscribing to a constant field. Over the initial render + 20 counter updates, the parent ran 21 times; the child ran **1 time** with injection and **21 times** with an explicit context prop. This is a component-call count in a controlled probe, not an app frame-rate measurement. Remove the prop from returned `{:fx/type child …}` descriptions. An ordinary helper explicitly called with a context during the same render is a different case.

   There is a retention cost as well. In a second isolated run with 100 updates and an 8-entry LRU, following only `:fx/context` references in cached child-description keys from the final context reached **101 cache atoms** with explicit props versus **1** with injection. Each old context also references its state map. The LRU bounds entries in *one* cache, not the number of old caches retained by those keys. This demonstrates the mechanism, not how much heap a running editor retains.

### Subscription hot spots that were measured

- **Vibes confirms this is larger than one tab.** A description-only traversal of the [starter Vibes tab](../src/laser_show/views/tabs/vibes.clj#L382-L424), including its 32-cell picker, occupied 574 distinct entries with sufficient capacity. With the app's 512-entry LRU, a beat-index-only change ran 128/128 view bodies again; with a 2,048-entry comparison cache it ran zero. Separately, the [always-mounted Vibes badge](../src/laser_show/views/root.clj#L95-L104) ran [full lint](../src/laser_show/subs.clj#L2043-L2060) when an unrelated effect's live `:active?` changed and the count didn't. Subscribe to structural inputs for this badge.
- **An unrelated cell edit invalidates open chain editors.** Both the [cue](../src/laser_show/views/dialogs/cue_chain_editor.clj#L247-L249) and [effect](../src/laser_show/views/dialogs/effect_chain_editor.clj#L88-L90) editors subscribe to *all* `:chains`. In a probe of the real effect-editor → list → sidebar description path, 600 unrelated edits left **all 601 context generations** reachable through child keys, even with the project's 512-entry LRU. Use the existing cell-addressed selectors. Strip context out of nested props as well as direct descriptions; avoid the cue editor's [per-render partials](../src/laser_show/views/dialogs/cue_chain_editor.clj#L307-L321) where stable data will do. [`list-ordered-ids`](../src/laser_show/subs.clj#L862-L875) also subscribes to all chains before resolving the path; the whole-DB fallback is not the path taken by the four production list constructors.
- **A per-cell lookup is only as narrow as its inputs.** [Selection](../src/laser_show/subs.clj#L269-L279) is read as one global coordinate in each cell display calculation. Moving selection across the effects grid rebuilt 32 display maps for two changed values. Separately, adding one *Vibe* binding reran all 32 unchanged wrappers on each grid: [cue](../src/laser_show/views/components/grid_cell.clj#L295-L304) and [effect](../src/laser_show/views/components/grid_cell.clj#L475-L483) cells subscribe to and scan the entire trigger map. Return a per-cell boolean for selection/learning; index bindings once, then subscribe to the value for the cell.
- **Move expensive work out of `sub-val` leaves and oversized keys.** [`playing-cues`](../src/laser_show/subs.clj#L310-L325) sorted on each of 20 unrelated stats changes even though its outer result stayed identical. [`pattern-fold`](../src/laser_show/subs.clj#L1186-L1190) received 64 rates with unchanged zones and calculated the same text 64 times; [the fold uses just the lane](../src/laser_show/routing/zone_patterns.clj#L375-L385). Derive the sort from the subscribed cue inputs and key the fold by what it reads. No delayed bound-context read was demonstrated in the audited selectors; sorting data already extracted is different from subscribing during lazy realization.

## Document, undo and asynchronous work

- **A serialized event queue does not fence an old app instance.** During a same-JVM restart, [stop ignores a timed-out flush](../src/laser_show/app.clj#L325-L340), and [start-test! replaces the context on its caller's thread](../src/laser_show/app.clj#L381-L396). A handler holding the old snapshot across that timeout restored the old document marker after replacement. A separate held [discovery completion](../src/laser_show/events/core.clj#L278-L287) also updated the new rig after a *successful* flush: the [recipient accepts the result without a request or instance ID](../src/laser_show/events/handlers/projector.clj#L231-L240). Serialize context replacement with commits; ignore completions from retired instances and superseded scans. This is distinct from two app agents running concurrently, which the shared executor already prevents.
- **A previous show's work can change the new one.** [New/Open](../src/laser_show/state/persistent.clj#L193-L222) resets document UI but keeps the backend learn target. [Learn completion](../src/laser_show/events/handlers/input.clj#L351-L386) checks target equality, not which document/request started it. A pending learn reproduced a new binding, dirty flag and undo step in the *new* show; a [pending OS paste](../src/laser_show/events/helpers.clj#L88-L104) also wrote to the new show. Conversely, [Open checks dirty state before the chooser](../src/laser_show/events/handlers/menu.clj#L82-L106), but [applies the result](../src/laser_show/events/handlers/menu.clj#L122-L129) even if an edit landed while it was open. Give document-bound work a document/request identity, invalidate it on replacement, and recheck a destructive continuation against current state. The [zone-map switch's ID check](../src/laser_show/events/handlers/timing.clj#L185-L192) is a working precedent. Moving ZIP I/O off-thread is a [separate, explicitly deferred issue](2026-11-07-improvement-review/00-overview.md#L45).
- **A “flushed” rig write can still be in flight.** [The writer](../src/laser_show/state/rig_store.clj#L269-L308) clears `!pending` *before* I/O, and `flush!` returns true when that slot is empty. With a blocked fake write, `flush!` returned true while the write was still running. [Shutdown](../src/laser_show/app.clj#L298-L306) can then release the lock without having drained it. Also, [a successful retry](../src/laser_show/events/handlers/rig.clj#L111-L120) can resume a [previously authorized Exit](../src/laser_show/events/handlers/menu.clj#L55-L66) after the show has gained unsaved edits. Track queued and in-flight generations, wait for the writer to settle before unlocking, and recheck current dirty state before continuing Exit.
- **Background beats can keep a missed gesture's Undo transaction alive indefinitely.** [History middleware](../src/laser_show/events/handlers/history.clj#L299-L311) touches an open transaction on a changed document *root* before testing whether undoable content changed. `:timing` contains both BPM and the [beat index delivered by clock status](../src/laser_show/services/show_clock.clj#L186-L203). After 125 seconds of simulated beat reports, the transaction was still open; an unrelated edit got no separate undo entry. Refresh the deadline for an undoable edit belonging to the gesture, not for a status update.
- **Some restored identities have only half their state.** [Moving an effect cell](../src/laser_show/vibes/refs.clj#L118-L134) also moves the vibe's ownership; [Undo](../src/laser_show/state/history.clj#L268-L315) restores activation at the old cell without moving ownership back, so the next vibe and [Save](../src/laser_show/state/persistent.clj#L124-L136) can leave that effect on. Likewise, removing and undoing the last member of a rig-only group restores its membership without its definition: [group copy](../src/laser_show/state/rig_file.clj#L46-L64) and [autosave](../src/laser_show/events/handlers/rig_autosave.clj#L28-L34). Restore these references and their definitions together. On Open, the [shared pin remapper](../src/laser_show/state/rig_file.clj#L113-L123) also misses references inside pattern/step-grid data; test the whole document's reference round trip, not just the cue target.

## Device and runtime boundaries

- **A clock report can turn transport playback back on after Stop.** [Stop](../src/laser_show/events/handlers/timing.clj#L92-L101) sets `:playing? false` and retains cue intents. [The clock](../src/laser_show/animation/show_time.clj#L227-L235) can subsequently report a cue ending. [Its handler](../src/laser_show/events/handlers/timing.clj#L160-L166) calls [`deactivate-cue`](../src/laser_show/animation/cue_timing.clj#L348-L355), which derives `:playing?` solely from whether any other cue remains. Verified with two intents and the real handlers: **playing → Stop: false → cue-ended: true**, with no Play event. Cleanup may turn playback off when the last cue ends; it should never turn a stopped transport on. Test Stop followed by delayed end reports and by a seek that supersedes an earlier completion. This was a state-transition probe, not an output test.
- **Opening devices blocks every other event.** [MIDI refresh/connect](../src/laser_show/events/handlers/input.clj#L51-L69) and [OSC server start/stop](../src/laser_show/events/handlers/input.clj#L149-L172) perform device I/O inside handlers. A gated fake MIDI refresh ran on `laser-show-events`; a tap and queue marker could not run until it returned. Repeated [MIDI auto-connect](../src/laser_show/input/midi.clj#L278-L285) also opened two receivers for the same fake device; both delivered the same note. Make opening/closing an idempotent effect on a device worker, with handles owned there and request/status data fed back to the event thread. Actual device latency was not measured.
- **Learn All can remove its next step's listener.** The [callback](../src/laser_show/events/handlers/input.clj#L291-L316) delivers a promise and then removes a shared router key. [Completion can already have started the next step](../src/laser_show/events/handlers/input.clj#L361-L394) before that removal. A gated probe reproduced a wizard waiting for ACCENT with no listener. Key registration, cleanup and completion to the *attempt*, not just the target or one shared registration key. A related case: the trigger editor allows behavior changes mid-learn, but [the completion writes the originally captured action](../src/laser_show/events/handlers/input.clj#L380-L386); either commit the currently displayed choice or freeze it for that attempt.
- **Switching off Follow Timecode can leave a cue playing in the runtime.** [Chase starts with its previous active map](../src/laser_show/animation/show_time.clj#L201-L205); [non-chasing definitions are skipped](../src/laser_show/timeline/playback.clj#L73-L82), and [stop reports are also conditional on still being a chasing definition](../src/laser_show/animation/show_time.clj#L230-L235). Synthetic ticks reproduced a stale run and then two entries for the same cell after manual play. Prune removed/disabled chase entries and reconcile only the matching old intent so a newer manual run is preserved.
- **The output thumbnail shows an attempted frame as sent.** The [provider records the frame](../src/laser_show/backend/multi_engine.clj#L272-L282) before [sanitizing, sending and handling failed sends](../src/laser_show/backend/streaming_engine.clj#L400-L439). The display can continue to label attempted content “Laser output” even when a driver rejected it or an empty recovery frame was sent. Publish the last successful driver return (including a successful empty recovery frame) or explicitly label the preview as generated/unknown. This is a source-traced distinction, not an assertion about physical delivery.
- **A held non-keyboard input can release the wrong action after rebinding.** The [keyboard path](../src/laser_show/events/handlers/triggers.clj#L187-L197) remembers the press action, but other sources resolve the *current* binding at release. Retain the original action by physical input until release/cancel. Two smaller publication gaps: [the gamepad](../src/laser_show/input/gamepad.clj#L73-L76) compares axis movement with the last *sample*, not the last [value emitted](../src/laser_show/input/gamepad.clj#L101-L123), so a smooth slow sweep can fail to update a meter; [Map cycle](../src/laser_show/services/show_clock.clj#L239-L251) omits the already sampled input values from its modulation context, allowing [a macro](../src/laser_show/animation/modulator_evaluators.clj#L257-L266) to stay at default while its meter moves. Fix those bridges at their owners without routing every sample through the UI database.

## Boundaries to keep

- The recent state-integrity work (`09b6db7`..`7412ac6`; the plan is deleted and in git history) addressed the old concurrent-writer, clipboard, and mid-frame app-state reads. The [runtime write guard](../src/laser_show/state/core.clj#L108-L128) throws in dev/tests; production logs and still performs a prohibited write. [Kondo](../.clj-kondo/config.edn#L11-L38) flags the direct writers. The defects above can happen **with** one writer: serializing two events doesn't make a stale payload current.
- The [show clock](../src/laser_show/services/show_clock.clj#L258-L304) reads the app state for its tick and publishes the resulting snapshot separately. The [ordinary preview](../src/laser_show/views/components/clock_view.clj#L31-L76) draws on FX pulses and stops its timer with the node. Human-readable [clock status](../src/laser_show/services/show_clock.clj#L176-L203) goes back through events. Putting every rendered frame or fader sample in app state would turn a good runtime boundary into more UI work.
- [The scene's keyboard filter](../src/laser_show/views/key_triggers.clj#L35-L61) needs an immediate decision about consuming a native event. Reading a fresh snapshot **at key time** is appropriate; its [scene-owned cleanup](../src/laser_show/views/key_triggers.clj#L64-L90) illustrates what to pair with native setup. The same raw read inside a label's description would be a missing dependency.

## Recommended order and verification

1. **Protect the user's document and transport.** Pin the numeric-Enter round trip and rejected Open, Stop followed by cue completion, Delete after retarget, Step Grid after reorder, and the refused rig checkbox. The first three are captured in the state-outcome probe. Use real JavaFX events for the control bugs and pure transitions for the transport and document invariants. Add the custom-group AUDIENCE parity case alongside the existing direct-group test.
2. **Give asynchronous work an owner and a lifetime.** Address document replacement, retired app callbacks, device/learn request IDs, rig write completion, and unfinished gesture transactions. Test stale completions, reversed completion order, and close/reopen. A successful event-queue flush says nothing about an unfinished worker or a rendered control.
3. **Restore selective rendering.** Remove explicit bound contexts and stale callback registries first; then narrow the chain/grid subscriptions and measure a bounded cache on Grid, Vibes and an open editor. Keep a whole-view call count as well as local selector tests. This order avoids retaining more old contexts by simply enlarging the cache.
4. **Bring developer feedback in line with reality.** Fix the renderer option wiring, correct the read helper docstrings and lead the state guide/refactoring prompt with the app-specific rules above.

**Evidence:** Both linked scripts ran with JavaFX headless on macOS arm64. The numeric probe uses the actual field description and handlers and reads/writes a ZIP entirely in memory (the EDN parse error is the reproduced symptom). The editor probe exercises the mounted test app's native key filter. The separate checkbox check observed the actual mounted control after the queue and render. Other rows identify handler/selector probes or source-traced cases; the selectors review also ran 10 existing tests (65 assertions passed). These are targeted checks, not a full-suite run, a heap profile, an FPS benchmark, or hardware tests. No production code was changed.
